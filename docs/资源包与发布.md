# 资源来源、域名配置与发布

> 这份文档回答三个问题：**素材从哪来**、**下载地址怎么藏**、**官方上新了怎么办**。
>
> 注意：早期版本是"维护者自己打 zip 资源包 → 上传 → 用户下载"，那套已经废弃，
> 现在全部走**官方 CDN 直连 + 本机解包**。旧脚本（`tools/build_packs.py`、
> `tools/make_pack_archives.py`）保留但不再是主路径。

---

## 1. 素材从哪来

游戏是 Unity WebGL 项目，资源以 **AssetBundle** 形式放在官方 CDN 上：

```
https://<官方CDN根>/choukou/AssetBundles/bundle_scenarioscript_char_1
                                              bundle_voice_adv_char_1_0 … 5
                                              bundle_bgimage_<hex>
                                              bundle_standimages_stand_<num>
                                              bundle_chara_c-panel_<cid>
```

一共 **25,204 个包 / 24.66 GB**（`Manifest1Ex` 17,133 个新资产 + `Manifest2Ex` 8,071 个旧资产，
后者含分层立绘，缺了会漏资源）。

客户端不做"整站预构建"，而是**按剧情按需取**：用户勾一部剧情，只下它引用的那些包。

| 类型 | 命名规则 | 落地产物 |
|---|---|---|
| 剧本 | `bundle_scenarioscript_char_<cid>` / `_main_<n>` … | `web/data/char_<id>.js` / `adv_<kind>_<no>.js` |
| 语音 | `bundle_voice_adv_char_<cid>_<seg>` | `web/media/audio/<cid>/*.m4a` |
| 半身像 | `bundle_chara_c-panel_<cid>` | `web/media/img/avatar/<cid>.webp` |
| 背景 | `bundle_bgimage_<hex>` | `web/media/img/back/*.webp` |
| CG | `bundle_eventimage_<id>_<num>` | `web/media/img/cg/*.webp` |
| 立绘（分层） | `bundle_standimage_stand_<num>_<cloth>` | `web/media/img/stand/*.webp`（需合成表情差分） |
| 立绘（完整） | `bundle_standimages_stand_<num>` | 同上，`*_base` 的兜底 |

**实测注意**（都在 `server/cdn/net.py` 里处理了）：

- CDN **支持 Range**，但单连接只有 **60–100 KB/s**，瓶颈是每条连接的吞吐和 TLS 握手
  → 必须并发，32 连接约 7.7 MB/s，64 连接约 16 MB/s
- **不要给 URL 加 `?x=2510062231` 这类参数**：那是前端缓存破坏参数，过几天就 404
- 完整性校验只认清单里的 `size`（逐字节精确）；`hash` 是 Unity 打包期的 Hash128，
  **不是** md5，只能当"版本指纹"用

## 2. 资源清单（Manifest）

清单是"有哪些包、多大、依赖谁"的唯一真源，也是增量更新的入口。

```
GET https://<官方CDN根>/choukou/AssetBundles/Manifest1Ex
  → Base64 文本（约 3.5 MB）
  → base64 解码
  → AES-256-CBC 解密（KEY/IV 在 server/cdn/config.py，社区公开值）
  → JSON：{"data":[{"bundle_name":…,"crc":…,"size":…,"hash":…,"dependencies":[…]}…]}
```

程序里的位置：

- **不入库**：`Manifest*Ex.json` 全部在 `.gitignore` 里。清单随官方更新变化，
  打包进仓库只会让用户拿到过期数据 —— 而且"检查更新"的第一步本来就是下载它，
  所以没有必要带。
- **存放**：`userdata/cdn/Manifest1Ex.json` / `Manifest2Ex.json`（旧版备份成 `.prev.json`）
- **首次使用**：控制台会显示"还没有资源清单 → 下载资源清单"（约 5 MB，带进度），
  也可以在「更新 → 刷新官方清单」里做
- **耗时**：装了 `cryptography` 约 16 秒（下载 5 MB + 解密）；只有纯 Python 实现时要 60 秒以上

> 解密实现有两套（`server/cdn/aes.py`）：有 `cryptography` / `pycryptodome` 就用（毫秒级），
> 没有就退回内置纯 Python 版本（慢但正确，带 FIPS-197 自检）。

## 3. 下载地址怎么"藏"

要求：仓库里不出现明文直链，运行时才解密；域名将来变更时用户能自己改。

### 3.1 内置默认值

`server/cdn/config.py`：

```python
CDN_BASE_DEFAULT = "https://<官方CDN根>/choukou/AssetBundles/"
```

### 3.2 加密存放（可选但推荐）

```bash
python tools/encrypt_links.py --path choukou/AssetBundles
python tools/encrypt_links.py --show           # 自检解出来是什么
```

写入 `web/data/packs.links.js`：

```js
window.__PACK_LINKS="M2KwaapU0tU0CrCCeWg33ZtE+wO9tcEwsXrGmJoCgwzV/yYNNRgwsSY+j4T3AxAgdis8xXc4l3kd9e7L…";
```

RC4 + base64，168 字符。解出来是：

```json
{"cdn": "https://<官方CDN根>/choukou/AssetBundles/", "base": "", "overrides": {}}
```

两端都能解，且**逐字节一致**（已验证）：

- `server/packs.py` 的 `deobfuscate()` → 后端下载用
- `web/assets/js/links.js` → 前端自检 / 纯静态部署时用

> 混淆不是安全措施，只是不让明文直链被搜索引擎和爬虫索引。真正的访问控制请用存储侧策略。

### 3.3 用户自定义（防官方域名变更）

三级优先级，后者覆盖前者：

1. `config.py` 的 `CDN_BASE_DEFAULT`
2. `web/data/packs.links.js` 加密值里的 `cdn` 字段
3. `userdata/links.json` 明文（用户自己改，或控制台「设置 → 下载源」里填）

```json
{ "cdn": "https://你的镜像/choukou/AssetBundles/" }
```

改完立刻生效（`config.cdn_base()` 每次现取，不重启）。**这条路径就是为了
"官方哪天换域名了，用户不用等新版程序"**。

## 4. 官方上新了怎么办

1. 用户点「更新 → 刷新官方清单」
2. 程序重新拉 `Manifest1Ex/2Ex` → 解密 → 对比本地记录
3. 报告"云端共 N 部剧情，新增 M 部"，并列出来
4. 用户勾选安装即可（新角色就是新的 `char_<cid>`）

不需要发新版本程序 —— 清单是数据，不是代码。

## 5. 发布程序本体

**发版只看 `VERSION`，不用自己打 tag：**

```bash
# 1. 改 VERSION（比如 1.0.4 → 1.0.5）
# 2. 推上去
git push origin main
```

CI（`.github/workflows/release.yml`）的判定顺序：

| 情况 | 行为 |
|---|---|
| push 到 `main`，没动 `VERSION` | **不触发** —— 连一次 Actions 运行都不会创建（`on.push.paths` 在事件层过滤） |
| push 到 `main`，动过 `VERSION` | 打包 + 发 Release |
| 动过 `VERSION`，但该版本的 tag 已存在 | 跳过（不覆盖已发布的版本；真要重打同版本去 Run workflow） |
| Actions 页面 Run workflow | 总是打包（`publish` 关掉就只留 Artifacts） |

> `paths` 比的是**这次 push 全部提交的合计 diff**，不是只看最后一个提交：
> 一次推 5 个 commit、其中某个改了 `VERSION` 也会触发；"先推代码、再推版本号"两次 push
> 同样没问题，第二次打包的 HEAD 已经包含第一次的提交。

打包内容 = **这次运行的 HEAD（main 最新）**，不是某个 tag 的快照 —— 这是 2026-11-02 改的：
以前是 `push: tags: v*` 触发、checkout 检出 tag 指向的提交，于是"打完 tag 之后又 push 的修复"
永远进不了同版本的包（v1.0.4 的 tag 停在 `9c930ef`，其后还有 3 个提交没进包）。

构建步骤：

1. 装 `requirements.txt`（UnityPy / lz4 / Pillow / numpy / cryptography）
2. 自检：后端 import、前端 `node --check`
3. 组装 `*-update.zip`（纯代码：server/ web/assets/ tools/ docs/ VERSION，3–5 MB，给自动更新用；**不含 i18n 译文**，那是用户数据）
4. 组装 `*-win64-portable.zip`（内置 embedded Python 3.11 + 全部依赖，解压即用）
5. 发 Release，并把 tag `v<版本>` **对齐到这次构建用的提交**（以前 tag 已存在就静默跳过，
   于是 `git checkout v1.0.4` 拿到的代码和包里的不是一份）

发布前记得：

- 改 `VERSION`
- 改 `web/data/app.json` 的 `repo`（CI 会用 `${{ github.repository }}` 自动替换，一般不用管）

> **同版本不会重发**：程序里的更新检查只比较 tag 号（`server/updater.py` 的 `_ver_tuple`），
> 所以"VERSION 不变、只覆盖 Release 附件"对老用户没有意义 —— 他们收不到。
> 热修请 bump `VERSION`；确实要用同一版本号重打（比如刚发的包坏了、还没人升级），
> 去 Actions 页手动 Run workflow 即可，它同样用最新提交打包。

### 下载地址（只有版本号会变）

| 包 | URL 模板 | 谁用 |
|---|---|---|
| 便携包（给新用户，内含 Python） | `https://github.com/<repo>/releases/download/v<版本>/ESCAH-Offline-v<版本>-win64-portable.zip` | **手动分享给别人**；文档里记一份即可 |
| 更新包（纯代码，~1 MB） | `https://github.com/<repo>/releases/download/v<版本>/ESCAH-Offline-v<版本>-update.zip` | 程序自动发现，**不用人工干预** |

当前 v1.0.5（`<repo>` = `allindusk/escahoffline`）：

```
https://github.com/allindusk/escahoffline/releases/download/v1.0.5/ESCAH-Offline-v1.0.5-win64-portable.zip
https://github.com/allindusk/escahoffline/releases/download/v1.0.5/ESCAH-Offline-v1.0.5-update.zip
```

> 国内直接下 GitHub 很慢（实测本机直连 0.7 MB/s，还经常握手失败）。
> 把整条 URL 粘在反代后面能快一个数量级。程序内置的线路顺序（**不测速，
> 有响应就用**）：`https://gh-proxy.org/` → `https://v4.gh-proxy.org/` →
> `https://v6.gh-proxy.org/` → `https://cdn.gh-proxy.org/` → GitHub 官方直连（兜底）。
> 线路名单在 `server/mirrors.py` 的 `GH_ROUTES`，测速脚本 `tools/_gh_route_bench.py`
> （仅供研究，程序本身不跑测速）。

### 更新流程

> **启动检查是可选的、而且只查不装**：控制台「更新」页的
> 「每次启动程序后检查更新」勾选框（默认勾选）打开时，启动后会发**一次**
> release 查询，只用来在页面顶部挂"发现新版本"的提示；**不下载、不重启**。
> 取消勾选后启动时零网络请求。除此之外没有任何定时/轮询任务。

1. 用户点控制台「检查程序更新」→ `GET /api/update/check` 发**一次** release 查询
   （GitHub API → 反代 → `releases.atom` 三级兜底）→ 页面上告诉你是"已是最新"还是"发现新版本"
2. 有新版本 → 点「下载并应用」→ `POST /api/update/apply`：下载 `-update.zip`（约 1 MB）
   到 `userdata/update/staging` → 起独立更新器 → 主进程退出 → 按白名单覆盖
   `server/` `web/assets/` `web/*.html` `tools/` `docs/` `VERSION` → 自动重启
3. 页面发现版本号变了 → 顶部提示「刷新页面」，刷新后新功能生效

**为什么下载/替换不自动做**：① 替换 `server/` 必须杀掉本进程，用户可能正在看剧情，
突然中断体验极差；② 大文件下载要占带宽，什么时候下由用户决定。
`web/media`、`web/data`、`userdata`、`web/assets/i18n` 永不覆盖。

> 如果更新中途被中断（例如手动杀进程），暂存区会留着已下载的新版本：
> `/api/state` 的 `updateReady` 会带上它的版本号，页面顶部挂「重启并完成更新」，
> 点一下就能接着装完（不会再重新下载）。

## 6. 常见问题

**Q：能不能只发一个角色给朋友，不让他下素材？**
把 `web/data/` 和 `web/media/` 里该角色的产物打包给他，他解压覆盖即可（这就是旧 zip 模式）。
程序不禁止，但注意素材版权（见 NOTICE.md）。

**Q：清单刷新失败？**
检查 CDN 是否可达、`userdata/links.json` 的 `cdn` 有没有写错。错误信息会原样显示在页面上。

**Q：装到一半失败了怎么办？**
重试即可。已经下完的 bundle 在 `userdata/char_story/files`、`files_img`、`files_audio` 里，
按 `size` 校验跳过，不会重下。

**Q：bundle 缓存占地方，能删吗？**
可以删 `userdata/char_story`、`userdata/files_img`、`userdata/files_audio`（不删 `userdata/cdn`）。
删了只是下次装剧情要重新下载。
